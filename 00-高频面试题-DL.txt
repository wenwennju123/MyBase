Redis使用场景-分布式锁的实现
	分布式锁：在分布式多线程环境下，多个节点对共享资源同时访问造成的数据安全问题，通过锁机制来实现资源访问互斥，避免因竞争导致数据不一致。
	Java中的线程锁：synchronized、Lock

	分布式环境下，一定要首先明确 锁（互斥）的范围。
	锁一般会设置在公共的位置，需要加锁的可能竞争的一定都要经过此公共位置。
	多个请求（线程） 先来redis中获取锁，持有锁的可以操作数据库，操作完成释放锁。剩余的在外面等待锁。

Redis实现分布式锁的方式
	Jedis、Lettuce、RedisTemplate、Redission、
	本质上的redis命令是  setnx-expire-del

	Redission相对于Redis就是MyBatis相对于MySQL的关系、更加成熟且提供了高效的接口与方法来操作redis
	
	setnx  就是 set key if not exist。不存在就设置key，已经存在就不设置。
	expire  就是 设置 锁的key 的过期时间、防止死锁。
	del 就是 释放 锁的key 

	redis通常是直接用String数据结构来完成锁的存储

原生代码举例：
	// 为1则标识成功，0失败
	result = redisConnection.setnx(lock_key, unique_value);
	
	redisConnection.expire(lock_key, 30);
	// 持有锁的执行业务
	ServerService.exceute();

	redisConnection.del(key)

	可以使用lua脚本保证redis对锁操作的原子性

Redission源码解析  RedissionLock.java
	getLock方法  返回RedissionLock 即 RLock
		为锁名 lock name 提供id 使用UUID生成，并获取该锁的超时时间 默认30000ms，拼接key为 this.entryName = id + ":" + name；
		并初始化发布订阅 pubSub
		在redis告诉状态下，个数较少内容简单的字符串可以直接使用拼接的形式

	lock.lock()方法
		默认施放时间 leaseTime 是 -1 不会主动释放
		首先获取当前线程id
		使用 tryAcquire(waitTime, leaseTime, unit, threadId)  获取锁   unit是时间单位，默认毫秒ms。waitTime是获取不到锁的等待时间
		该方法底层 evalWriteSyncedAsync()  是使用了lua脚本来执行redis命令
			该脚本中使用了 hash结构 来存储，使用的命令就是 hexists 和 hincrby。
			锁的key具有两个值，一个是key的id，一个是key的状态（value），value为 1 标识该锁生效
			"if((redis,call('existsKEYS[1])==0)”+                 // 判断存不存在
			"or(redis.call('hexists', KEYS[1], ARGV[2]) == 1))then "+    // value  即重入count 为 1
			"redis.call('hincrby', KEYS[1], ARGV[2], 1); ” +			// count + 1 自增
			"redis.call('pexpire', KEYS(1], ARGV[1]); ”+      // 设置过期时间
			"return nil; “+
			"end; " +
			"return redis.call( 'pttl',KEYS[1]);"
		Lua脚本将锁的创建以及设置过期时间放在同一个操作步骤下完成，保证了多个redis命令执行的原子性（就相当于当作一条去执行）

	锁的续期
		假如锁的过期时间是30s，但是业务执行了40s，锁将要过期时业务却没有执行完成。业务代码失去了锁的保护，导致竞争。
		引入了锁的续期，保证业务执行期间锁不会过期。
		就需要一个新的线程来进行监测，业务没有执行完就将锁的超时时间进行延长。
		Redission实现：
			sheduleExpirationRenewal(threadId)
			核心方法 renewExpiration();

				// 内部使用了 io.netty 框架的 Timeout 接口, 创建了周期定时任务。并提交给 ServiceManager 来执行
				// 让该定时任务的线程，不断地为锁进行续期
				Timeout task = getServiceManager().newTimeout(new TimerTask(){
					// 定时任务的核心实现 run 方法
					@Override
					public void run(Timeout timeout) throws Exception {
						ExpirationEntry ent = EXPIRASTION_RENEWAL_MAP.get(getEntryName());
						if (ent == null) {
							return;
						}
						Long threadId = ent.getForstThreadId();
						if (threadId == null){
							return;
						}

						// 核心续期方法
						// 内部也是调用了lua脚本 保证hexists 和 pexpire 命令的原子性
						CompletionStafge<Boolean> future = renewExpirationAsync(ThreadId);

						future.whenComplete((res, e) -> {
							if (e != null){
								log.error("Can't update lock {} expiration", getRawName(), e);
								EXPIRASTION_RENEWAL_MAP.remove(getEntryName());
								return;
							}
							if (res) {
								// reshedule itself
								renewExpiration();
							} else {
								cancleExpirationRenewal(null);
							}
						});
					}
				// 这步骤就是在 设置定时任务的 周期 为：锁过期时间的三分之一，开始续期。默认就是30/3=10s续期一次
				}, internalLockLeaseTime / 3, TimeUnit.MILLISECONDS);

				//启动该任务
				ee.setTimeout(task);

	unlock方法
		在finally语句块中执行，
		方法 unlockAsync0(threadId)
			方法 unlockInnerAsync(threadId, id, timeout)
			核心依旧使用了lua脚本来进行释放，保证一系列列redis命令 例如 redis.call('pexpire', KEYS[1], ARGV[2]); 'del'  'set' 'count'

Redisson实现的分布式锁是可重入的
	锁的重入，即锁可以被重复获取。当线程A获取到锁A后，线程A再次获取锁A还是可以获取到的。
		java中的 synchronized、ReentrantLock都是可重入锁

	单机测试举例：

								直接lock.unlock()  会释放 value 为 2 的锁， 1 的不会释放
								那么在末尾就需要将这两个锁全部释放
		
			...
		}finally {
			...
			
			lock.unlock();
			
			// 获取了几个锁，就得释放几次
			lock.unlodk();

			...
		}

实现分布式锁需要注意的问题：

	保证原子操作
		redis原生： lua脚本 执行 setnx 和 expire 命令
			或写为一句命令  linux> set lock 123 nx ex 30
							OK
							linux> keys *       查看所有key
		使用Redission

	确保锁的释放
		try catch finally 保证手动释放锁。
		设置合理的过期时间，自动释放

	释放了锁但是业务还没执行结束
		锁的续期，redission “看门狗”机制 自动续期，默认按照过期时间的三分之一自动续期

	释放了其他线程的锁
		如果没有锁的自动续期，A业务执行时间超出了A锁的自动释放时间，导致锁被B业务获取。进而导致A执行完后手动释放，释放的是B持有的锁。
		原则：自己的锁自己释放
		解决方法，为每个线程设置UUID，用于标识该线程持有的锁。手动释放时，判断一下是否是自己持有的锁

	大量请求竞争锁失败
		重试
			自旋，重试3~5次，可以逐次增加等待时间以降低压力。都没有获取到则返回获取锁失败
		优化业务执行流程，锁的粒度
			锁只保护需要保护的，而不是整个完整的业务
		限流
			GateWay，Nginx等

	多节点Redis主从复制的问题
		A在Master节点中获取了锁，锁需要复制到从节点 Slave中。主从复制具有一定的延迟。如果未复制完，Master发生故障，
		经由哨兵选举。Master发生变化。其中并没有锁的信息。导致B拿到了锁，发生安全问题。

		redis官方的解决： 红锁 RedLock。 例如redis是 一主两从为一个节点，共三个节点的集群。
		加锁需要同时向所有节点中加锁。（复杂度提高了，实际中使用较少。redission中标识为已过期）
		判断 n/2 + 1 加锁成功，则整体加锁成功。少于 n/2 + 1,则认定为整体加锁失败
		如果各节点加锁总耗时，大于等于设置的最大等待时间，则直接返回加锁失败。

		更常用的实现：Redis集群不适合实现分布式锁，可以使用zookeeper来实现分布式锁
		CAP理论：一致性Consistency，可用性Availability，分区容错性Partition tolerance
		Redis的分布式锁是AP优先，强调高可用，允许短暂不一致，
		Zookeeper是CP的，强调一致性

	锁的性能问题
		优化：分段锁
			利用hash(uid) 进行分段。借用了ConcurrentHashMap的分段锁思想。
		举例 10000个请求，减1000库存。分段成 10个 1000请求 减100库存。或者 100个 100请求减10库存。
		维护的锁从 1 个，变为分段的 10个甚至100个锁。
		利用hash算法，取模等操作，将用户的请求均分为对应的段数，每段去获取相应的锁。
		合理取舍优化性能

	锁的可重入性
		redission实现的redis分布式锁是可以重入的，获取几次就要释放几次，由锁key对应的value值来存储，
			redission是lua脚本，里面维护了自增的value来实现的
		例如递归调用的时候，需要锁可以重入。

Redis缓存容易遇到的问题：缓存穿透（强调的是查询不存在的数据）
	缓存穿透是指 请求一个不存在的数据 而导致的
	例如使用攻击性网络爬虫一直请求不存在的数据，导致大量数据绕过redis直接访问mysql，导致数据库压力过大。

	解决方法：缓存空结果，对于数据库查询不存在的数据仍然缓存到到缓存中。例如 unKnow 字符串。有效减少数据库查询次数
		优点：实现简单。缺点：缓存无效数据，占用Redis内存。并且可能存在缓存与数据库不一致的情况。需要额外处理例如发送日志提醒，并设置过期时间

	解决方法：使用布隆过滤器。
		优点：不会缓存无效数据。缺点：实现复杂，存在一定的误判的情况。

	布隆过滤器在请求和redis之间生效，筛选掉不合理的数据。
	原理：布隆过滤器是用来检索一个元素是否在一个集合中的。 采用了一个很长的二进制数组，通过一些列的hash函数来比对该数据是否存在。
		在项目启动时，就可以将需要缓存的数据，需要布隆拦截的数据加载初始化，进行好hash运算。

	构成：二进制数组，hash函数（多组函数对数组长度取余数算出索引值，数组越长，hash次数越多，误判概率越低）
	代码实现举例：
		主要实现 bitmap 和 hash算法。
		实现的库：Guava（Google）、Hutool、Redisson、或者手写
	使用Redission获取
		redissonClient.getBloomFilter("name")
		// redission可以自动计算所需要的数组长度，依据添加的数据数量和容许的误判率。
		// 一亿数据，1%误判率，长度是967777042 (9亿 9亿字节，就是923MB)，hash函数个数7，总长度会大于 数据量乘以hash函数数量
		bvloomFilter.tryInit(expectedInsertions, falseProbability)
		bloomFilter.add();
		bloomFilter.contains();
		// 像这种过大的 value， redis较难在客户端进行展示。bloom-filter是一个String结构，value很大上百MB


Redis缓存容易遇到的问题：缓存击穿（强调的是热点数据，大量请求集中到几条热点数据）
	高并发条件下，对于热点数据热点key的访问占比很高，可能占80%左右。其余的是访问别的次级key。
	当热点数据失效的一瞬间，或者刚开始缓存中还没有对热点数据进行缓存构建，所有请求都会被发送到数据库去查询，导致数据库过载。

	解决方法：
		全局锁（分布式锁）
			保护数据库，减少对于数据库MySQL的查询访问。防止大量请求同时涌入数据库
			大量请求涌入redis，未命中缓存，在准备去查数据库时竞争锁，拿到锁的查询数据库，并将数据写入缓存。写入成功命中缓存并释放锁。
				进而其他请求相同信息的就可以直接命中缓存，无需查询数据库。
				锁的单位是锁同时查询某一个信息的多个请求。
		缓存预热
			将热点数据体检加载到缓存中，并设置较长的过期时间。甚至不过期（物理）。缺点：无法进行更新。
			逻辑不过期：物理上设置不过期，但是所存储的字段中增加一个 expire 过期时间字段标记。
				缓存逻辑时间与当前系统时间比较，未过期直接放回。
				过期了，返回过期数据的同时，获取一把分布式锁，没持有锁的直接返回旧数据，持有锁的开启新分支，
					开启一个异步线程去查MySQL并将新的数据更新到这个key，同时重新设置过期时间字段。（缓存重建）


Redis缓存容易遇到的问题：缓存雪崩（强调的是大量数据，甚至全部数据）
	缓存雪崩是指，在某个时刻，大量的key或者整个缓存的数据全部过期了。或者Redis服务宕机。导致所有请求直接落入数据库，数据库被压垮。

	解决方法：
		提高Redis的可用性，Redis Cluster集群，哨兵模式Redis Sentinel
		给不同的key设置不同的过期时间，避免短时间内大量的key过期。
		本地缓存，CDN分发网络缓存
		限流，熔断降级。请求窗口-失败率，时间窗口-平均耗时。

Redis每种数据结构最大能放多大的值（官网文档）
	String 512MB
	List 2^32 -1 = 4294967295 个元素 42亿
	Set 2^32 -1 = 4294967295 个元素 SortedSet相同
	Hash 2^32 -1 = 4294967295 个 field-value对。Hash类型仅受部署Redis的服务器上的总内存的限制，
		即多少个大Key多少个Hash是取决于内存里能放多少


保证数据库MySQL与缓存Redis的一致性
	延时双删，最终一致性。
	更新数据：
		先删除redis中对应key的缓存
		然后更新MySQL对应key的数据
		然后经过一定的延时，可以使用MQ延迟队列或者定时任务。再次删除redis中对应key的缓存。
		如果在这段延时过程中，该key又进行了更新，需要进入版本号或时间校验。校验不通过，延时删除redis缓存再进行延时


Redis集群最多可以部署多少主节点
	Redis Cluster 3.0后提供的，之前是Sentenal哨兵
	Redis集群的键空间被分为：共16384个槽位slot，最大节点数量理论也就是i6384个 2^14
	官方建议的最大节点数为1000左右

	每个主节点都负责处理 16384 个哈希槽的其中一部分。
	HASH_SLOT = CRC16(key) mod 16384 进行hash运算来判定

	集群间的通信协议 Gossip协议，每个节点都需要与其他节点建立集群链接 cluster bus
	n个节点，建立的连接数就是 (n-1) + (n-2) +...+ 2 + 1 是n的平方级别的。节点越多，节点间的通信所消耗的资源甚至会高于节点们本身。

Spring框架：Spring容器中的Bean是线程安全的吗（单例、构造注入、无状态）
	不是线程安全的
	Spring容器中的Bean默认是Singleton单例的，所有线程都共享一个Bean对象，是存在资源竞争的。

	但是单例Bean在实际使用中都是无状态的方式来使用。即线程之间的操作只会对Bean的成员执行查询。所以单例的Bean实际上是线程安全的。
	例如Controller、Service、Mapper、Dao、Entity、Domain 叫法不一样 等Bean大多都是无状态的，实际应用中不会对这些Bean中的属性进行修改，只需要关注方法本身。

	dao是承接从数据库查找出来的数据封装的对象，通常不会有多线程同时操作该dao。
	如果多线程共享某个Dao，例如要将其转换为dto，要修改dao中的数据，就需要引入锁的机制来保护。
	通常也不会这样做，而是在读取dao移动到dto去处理。

	并且Spring框架也是推荐构造注入，因为构造函数注入可以确保所有必需的依赖在对象创建时已经准备就绪，
	能够更好地支持 不可变性 和测试性，避免对象状态不完整的情况。构造函数注入还更符合依赖注入的原则，
	确保依赖关系是 显式的和不可变的。因此，现代 Spring 开发中更提倡使用构造函数注入，而不是 setter 注入。

	单例的注解：  
	@Scope(value = "singleton")

	如果Bean是多例的，每次访问就都会创建一个bean


Spring框架：如何保证Spring容器中的Bean是线程安全的（ThreadLocal）
	解决方法：
		将默认的singleton 单例的Bean改为 prototype 多例的Bean

		在Bean对象中避免定义可以变化的成员变量。

		如果Bean对象中需要定义可变成员变量，将可变成员变量保存在ThreadLocal中。
		本质上是使用了 ThreadLocal 线程隔离的特性，只有当前线程可以访问，其他线程拿不到数据
		private ThreadLocal<Integer> numberThreadLocal = ThreadLocal.withInitial(() -> {
			return 0;
		});

		多次也就是多个线程调用：
		numberThreadLocal.set(1)
		numberThreadLocal.get()

		ThreadLocal的应用： request response 对象，都使用了ThreadLocal进行了包装，其中包含的内容都是该次请求（线程）独有的
			每隔请求request之间都是隔离的。

Spring框架：事务的失效、传播行为
	情况举例：
		同一个Service中，方法a添加了事务，方法b没有添加事务。
		b方法调用了a方法：
			事务失效，不会触发回滚
			理解：Spring注解控制事务是AOP实现的，AOP的增强是一个环绕通知，方法前开启事务，方法结束，成功则commit，异常则rollback
			b去调用a本质上是将a的方法体挪到b里面执行，并没有触发事务注解，没有环绕通知，切点切不到方法里、没有调用代理对象等理解。

		a方法调用了b方法：
			正常生效， b 方法将在 a 的事务上下文中执行 传播行为是PROPAGATION_REQUIRED b的执行将会加入a的事务，不会重新创建一个事务。
			他们共同使用a的事务注解中定义的 rollbackFor等配置信息。			

		在不同的Service中，Service1的方法a添加了事务，Service2的方法b没有添加事务。
		b方法调用了a方法：
			正常生效，调用是通过 @AutoWired注入的代理对象调用的，具有增强的方法。

		a方法调用了b方法：
			正常生效， b 方法将在 a 的事务上下文中执行 传播行为是PROPAGATION_REQUIRED b的执行将会加入a的事务，不会重新创建一个事务。
			他们共同使用a的事务注解中定义的 rollbackFor等配置信息。		
		
	
	事务的传播行为：
		PROPAGATION_REQUIRED（默认值）：如果当前没有事务，就创建一个新的事务；如果已经存在一个事务，加入这个事务。适合大部分情况。

		PROPAGATION_REQUIRES_NEW：总是创建一个新的事务，如果当前存在事务，挂起当前事务。适用于需要在现有事务之外执行独立操作的情况。

		PROPAGATION_SUPPORTS：支持当前事务，如果没有事务，则以非事务方式执行。通常用于那些可选事务的情况。

		PROPAGATION_NOT_SUPPORTED：以非事务方式执行，如果当前存在事务，挂起当前事务。适用于明确不需要事务的情况。

		PROPAGATION_NEVER：以非事务方式执行，如果当前存在事务，抛出异常。适用于不允许事务存在的情况。

		PROPAGATION_MANDATORY：支持当前事务，如果没有事务，抛出异常。适用于需要强制在事务环境中运行的情况。

		PROPAGATION_NESTED：如果当前存在事务，则在当前事务中创建一个嵌套事务（可以独立回滚）；
			如果没有事务，则等同于 REQUIRED。适用于需要局部回滚的操作。

	PROPAGATION_REQUIRED（默认值）（当前没有就新建，有就加入）大部分情况推荐使用。
		没Required修饰直接调用a例如NotSupported，是不会创建事务的
	如果需要独立回滚，则可以选择 NESTED（嵌套） 或 REQUIRES_NEW（挂起当前）。
		例如b方法会抛出和a不一样的异常，单独进行捕获和回滚操作。

	实际：在类上添加 @Transtional修饰，修饰所有方法。并且避免在同一个类中直接调用 @Transtional修饰的方法。

	
	方法的修饰词： public protected default private final static 是否会影响事务生效
	只有public会生效，spring对于事务的管理，AOP的源码，反射机制中有对修饰符进行判断
		if(allowPublicMethodsOnly() && !Modifier.isPublic(method.getModifiers())){
			return null;
		}
	非public修饰的不会添加事务。前面的allowPublicMethodsOnly是读取自配置 configured，默认是 true。
	代理机制上：JDK只能代理public 和 CGLIB（包级私有）动态代理。
		AOP横跨多个模块，代理 类的对外接口是最合适的切点。
	Spring的设计原则上：强调业务逻辑的公开，保证公开操作的一致性完整性，private的私有方法内部逻辑不应该暴露。
		由public修饰的方法，去管理其他的private，protected方法的逻辑，即保护内部实现细节。
		Spring也会专注于管理public方法，是该类的公开API，是面向接口编程的思想体现。松耦合，易于测试

	
	多线程中的事务：
		情况：受事务保护的a方法执行中，开启了新的线程，该新线程中出现了异常。
			这时a不会回滚。也就是只会捕获当前线程发生的异常。
			new Thread(() -> {
				int a = 10 / 0;
			}).start();

	
	其他情况：
		可能操作的数据库引擎不支持事务，例如MyISAM引擎

RabbitMQ：如何保证消息的发送，接收的准确性，可靠的传递、不丢失。

	关键的四个步骤都需要成功：
		注意，想使用以下两个接口，就需要在初始化时，将本对象（消息的发送者、生产者）设置到rabbitRemnplate里面
		@PostConstruct
		public void init(){
			rabbitTemplate.setConfirmCallback(this);
			rabbitTemplate.setReturnsCallback(this);
		}
		确保生产者向交换机Exchange发送消息成功：
			使用 Confirm 确认模式，如果未投递成功，需要采取补偿措施例如重新投递，或者记录日志，或者通知其他组件例如运维监控或定时任务
			消息的发送者（生产者）需要实现 ConfirmCallback 接口，重写 confirm 方法。
			消息发送后（rabbitTemplate.convertAndSend(exchange, routingKey, json, correlationData)）会自动调用confirm方法
			在confirm方法中 判断消息是否发送成功（boolean ack），并进行相应的处理。
			常见错误：交换机指定错误，找不到交换机404
		确保交换机成功将消息投递到队列
			使用 Return 返回模式。
			消息的发送者（生产者）需要实现 ReturnsCallback 接口，重写 ruturnedMessaage 方法。
			消息发送后如果没能从交换机发送到队列，则会触发此方法ruturnedMessaage的调用，在其中记录日志或采取补偿措施。
			常见错误：路由键错误，路由键匹配错误。
		确保消息在队列中存储的可靠性（构建器模式）
			解决：交换机持久化、队列持久化、消息持久化、集群部署MQ
			默认情况下，交换机是持久化的  在RabbitConfig中对交换机声明时  .durable(true) 就是持久化
			默认情况下，队列也是持久化的，在RabbitConfig中队列声明时， 调用的 QueueBuilder.durable(queueName) 默认就是持久化的
			消息持久化到磁盘，避免消息丢失。处理消息体时 
				Message message = MessageBuilder.withBody().setDeliveryMode(MessageDeliveryMode.PERSISTENT).build()// 持久化投递模式
			使用RabbitMQ的镜像模式搭建集群。
		确保消费者可以成功从队列中获取消息
			方案：手动确认消息。
			@RabbitListener(queues = {})
			public void onMesssage(String msg, @Headers Map<String, Object> header, Message message, Channel channel){

				// 根据业务的执行结果来进行判断

				// 手动确认消息，消息销毁。 multiple: false
				channel.basicAck( , false);

				// 不确认消息，该消息重新入队等待下一次消费，一种重试策略
				// 需要避免死循环，需要限制重试次数，可以选择放入死信队列( , multiple =  false, requeue =  false)，或执行下一步的逻辑
				channel.basicNack( , multiple =  false, requeue =  true);

				channel.basicReject( , false);

			}


RabbitMQ：如何保证消息的幂等型（发送者发送重复的相同的消息，保证消费者不会重复消费相同消息）
							（在重复的场景下，生产者的目的或逻辑（对外）和消费者的目的或逻辑（对内）往往是不同的）
	唯一全局ID（唯一消息ID，redis去重或记录已经处理过的消息ID） 类比接口幂等性问题中的唯一请求ID以及缓存请求ID和结果。
	关键：保证消费者不会重复消息到相同的消息即可
	实现：例如使用 redis 的 setnx，确保消息id的全局唯一性。
		生成全局唯一ID，消息发送时，消息携带此ID。如果消息中具有唯一ID例如userId，orderID也可以直接使用。
		消费者消费时，检测一下 set id 1 nx，如返回ok 则代表该id的消息没有消费过（首次插入redis）。
		正常处理，返回nil则代表redis中存在，该消息已经消费过，不予处理。


RabbitMQ：死信队列的实现原理以及作用、应用场景
	死信队列：DLX 即 Dead-Letter-Exchange，就是死信交换机的意思。当一个消息在队列中变为死信dead message之后。
		它将被重新发送到另外一个交换机中，这个交换机就是DLX，绑定到DLX的队列就叫做死信队列。

	死信队列本身就是一个普通的消息队列，可以手动设置一些参数将其设置为死信队列。
		用来存放无法被消费的消息也就是死信的队列，
	
	死信队列可以避免消息一直无法被成功消费导致资源浪费，循环消费，消息挤压等情况

	死信的产生：
		Listener中channel.basicReject(, requeue = false) 消息被拒绝；
		Listener中channel.basicNack(, requeue = false) 消息未确认；
		或者消息过期 TTL；
			消息属性设置
			MessageProperties messageProperties = new MessageProperties()
			messageProperties.setExpiration("10000")
			创建时传入参数
			Message message = new Message(msg.getBytes(), messageProperties)

			可以对队列进行配置，在new 队列时候指定该队列的过期时间
			arguments.put("x-message-ttl", 10000)
		或者消息队列已满，消息被丢弃
			设置队列的最大长度
			arguments.put("x-max-length", 16)

	死信队列的配置：在RabbitConfig配置类中，配置directQueue()
	@Bean
	public Queue directQueue(){
		Map<String, Object> aarguments = new HashMap<>(8);
		// 指定死信交换机
		arguments.put("x-dead-letter-exchange", EXCHANGE_NAME_DLX);
		// 指定死信路由key
		arguments.put("x-dead-letter-routing-key", ROUTING_KEY_NAME_DLX);
		// 设置队列的最大长度
		arguments.put("x-max-length", 16)

		return new Queue(QUEUE_NAME, true, false, false, arguments)
	}


RabbitMQ：延迟队列的实现原理以及作用、应用场景
	延迟队列是用来存放延迟消息的队列。延迟是指消息被发送后，并不想让消费者立刻拿到消息并消费。而是需要等待指定的时间。
		等待了指定的事件后，消费者才可以拿到这个消息并消费。

	延迟队列的实现：
		引入延迟插件 rabbitmq-delayed-message-exchange
			实现了 Delay Exchange 延迟交换机
			Type: x-delayed-message
			Arguments: x-delayed-type=direct
			将消息持久化到内置的 Mnesia 数据库

		使用 TTL消息过期 + DLX死信队列来实现。
			原理：设置一个 给定TTL 的等待队列，消息先发送给等待队列，主动等待其过期。然后过期消息被送往 指定DLX。
				该指定的死信交换机可以与延迟队列共用一个交换机
				消费者再从指定DLX中进行消费。达到延迟的效果。
				如果根据业务需要不同的等待时间，就需要配置不同TTL的等待队列。


RabbitMQ：如何保证高可用性
	普通集群只复制队列的元数据，没有复制队列中的消息，消息依旧只保存在单机。不够高可用，不建议。

	集群部署+镜像队列机制
		节点间复制队列的元数据+消息内容。每个节点都拥有完整的队列信息及内容。
		节点间的通信以及复制会消耗较大的资源，性能与安全是不可兼得的。


RabbitMQ：如果有大量消息挤压如何解决
	原因：生产和消费失衡。
		例如生产消息很快（并发量高），但是消费消息很慢（执行速度漫）
	解决方案：
		预防：
			流量预估：预计每秒产生的消息数
			压力测试：压测消费能力的最大值
			应急预案：
		应急处理：
			生产端：限流：gateway
			生产端：熔断：降级
			消费端：削峰：缓存消息或者延时
			消费端：Kubernates自动扩容，自动增加实例数量
		事后总结并优化：
			优化业务流程，业务逻辑，优化数据库操作效率等方法提高消费者的消费效率。
			优化IO逻辑，使用异步处理等。网络IO的开销往往比磁盘IO开销大。
			体现个人观点与想法。
		安全性：
			避免因业务堆积导致消息丢失。
			合理设置TTL时间并指定死信队列DLX，之后再额外处理死信
			编写程序例如定时任务定时检测消息的发送与消费情况，补发或者其他的逻辑。

线程池 ThreadPoolExecutor ：核心参数（构造方法）以及其作用
	最多七个参数
	ThreadPoolExecutor threadPoolExecutor = new ThreadPoolExecutor(
		8,			// 核心线程池大小
		16,			// 最大线程池大小，当核心线程全部繁忙，且任务队列也存满。线程池会追加临时线程（非核心线程），直到总线程数达到该上限
		60,			// keepAliveTime 空闲超时自动销毁的时间，如果该线程空闲，且当前线程数大于核心线程池大小，超时销毁。默认不销毁核心线程
		TimeUnit.SECONDS,				// 上述空闲超时时间的时间单位  毫秒、秒、分、小时、天
		new ArrayBlockingQueue<Runnable>(1024),	// 阻塞队列、任务队列。指定容量大小。当核心线程全部繁忙时，任务加入队列等待被执行（缓存）。
		Executors.defaultThreadFactory(),				// 可为空。用于创建线程的工厂。支持自定义。
		new ThreadPoolExecutor.CallerRunsPolicy()		// 可为空。拒绝策略（包和策略）。当任务数量超过队列容量时，拒绝任务的策略。
	);
	线程池刚创建时，里面是没有线程的

	threadPoolExecutor.allowCoreThreadTimeOut(true)		//允许核心线程在 空闲超时后 销毁。默认为false，即保留所有的核心线程
	threadPoolExecutor.boolean prestartCoreThread()		//初始化一个核心线程
	threadPoolExecutor.int prestartAllCoreThreads()		//初始化所有核心线程

	线程名可以通过 Thread.currentThread().getName() 获取

	线程池提供的拒绝策略有：
		需满足 核心线程全部繁忙，线程池的任务队列workQueue已满，线程池的线程数达到最大线程池容量即非核心线程也全部繁忙。
			注意，此时的非核心线程也会从该任务队列workQueue中获取任务来执行，并没有额外的任务队列。
			注意，提供的四种策略均实现了 RejectedeExecutionHandler 接口，重写 rejectedExecution
		AbortPolicy（默认）：	直接丢弃新任务，并抛出 RejectedExecutionException 异常。
			方法会直接throw new RejectedExecutionException() 记录线程信息，而穿入的参数 Runnable r 不会执行
		DiscardPolicy：			直接丢弃新任务，不抛异常。
			相比于上一个拒绝策略，更为直接，不会抛出异常。
		DiscardOldestPolicy：	丢弃队列中最旧的（最靠前的）任务，然后尝试重新提交新任务，不会立即放弃新任务。
			if(!e.isShutdown()){
				e.getQueue().poll();	// 获取并移除队列头的元素
				e.execute(r);			// 尝试重新执行该新提交的任务
			}
		CallerRunsPolicy：		调用提交任务的线程自己执行任务。

		自定义策略：实现RejectedeExecutionHandler 接口，重写 rejectedExecution
			例如实现日志的记录，错误信息的记录以及结合上述的处理策略等。


线程池 ThreadPoolExecutor ：执行流程以及设置核心线程数

	主线程 ---- execute -----核心线程处理--不够了加队列----队列满了就创建非核心线程一起处理----还满就触发拒绝策略

	核心线程的设置计算公式：
		核心线程数 =  cpu的核心数 x cpu的可供使用的使用率 x (1 + 线程平均等待时间/线程平均计算时间)
		线程等待时间 与 计算时间 就是在一段时间窗口内，线程处于繁忙的占比和线程处于空闲状态的占比
		例如 60/40  80/20  50/50
		也就是计算时间耗时越短，理论可供使用的核心线程数越多

	核心线程的设置计算估计：
		将任务分为 cpu密集型（加密解密，循环，递归等）和 IO密集型（磁盘IO：数据库读写，文件读写，网路IO：网络通信，rpc调用）
		对于cpu密集的任务 设置：线程数 = cpu核心数 + 1
			+1 是为例防止线程偶发的缺页中断
		对于IO密集型任务 设置：线程数 = cpu核心数 * 2
			
	原则：单次任务执行的时间越短，就可以设置更多的线程

		同一个SqlSession两次相同的查询，但期间手动清空了缓存

HashMap：类继承结构与底层实现

									Map
		SortedMap     ConcurrentMap			AbstractMap			Hashtable

	HashMap:
		数据以键值对 K，V 方式存储的一种集合容器
		Key是不重复的，重复则 V 覆盖旧的。
		允许 K 为null，允许 V 为null 。取出来就是 “null” 说明HashMap对空值做了处理
		不保证k-v映射的顺序。无序的，输入的顺序与输出的顺序无关
		非线程安全
			本质：hash计算k，和插入v，是两步操作，没有锁机制来保证原子性。
			手动加锁就是
				synchronized(map){
					map.put(k, v);
				}
			更为严重的是扩容问题，如果多个线程同时触发扩容操作，在重新哈希的时候，可能导致链表的节点的引用指向自己，导致死循环。

	HashMap实现：数组 + 链表（查询 O(n)）/红黑树（查询 O(logn)）   since jdk 1.8
		Node节点： hash key value next
		数组默认长度16，初始化时必须指定长度。
		将 Key 通过 hash 运算，然后对数组长度取模（位运算）决定其所在的数组下标
		链表长度达到 8 后，转换为红黑树。如果元素删除，红黑树节点数量降低至6，可以转换回链表
		默认负载因子是 0.75， 元素数量超过容量 * 负载因子时，触发扩容，容量翻倍。
			触发扩容会重新哈希，并且将原数组中的所有键值对重新插入到新的数组位置。确保均匀分布。开销很大。
		数组下挂的链表和红黑树是用来解决哈希冲突的，当不同的key经过hash运算取模后，可能发生落在同一个数组槽位（下标）上的情况。
		这时就会使用链表来进行存储额外的键值对。

	HashMap默认容量 16 初次扩容发生在第13个数据插入。第13个就触发扩容说明前12个全都直接存在数组中。没有hash碰撞。
		那么此时hashmap中也就没有链表，更没有红黑树。就是简单的数组结构。
		只有在大量数据发生hash碰撞时，才会触发链表存储发生碰撞的节点。
		不同槽位可能同时存在链表和红黑树或仅有该节点，取决于hash碰撞的概率。
		如果hash函数计算得足够平均，在hashmap允许扩容的情况下，很有可能不会触发红黑树转换，而是先触发扩容。
		hashmap的扩容是必然触发的，想要避免就设置更大的初始容量和负载因子并设计合理的哈希算法

HashMap：多线程下的安全问题
		jps -l   查看所有java线程编号及运行者的信息
		jstack   查看对应线程编号的堆栈信息
	
	多线程put 导致死循环：
		本质：扩容，重新哈希，链表节点指向自己

	多线程put 导致元素丢失：
		本质：hash计算k，插入v多线程下不是原子的，竟态，hash冲突，发生覆盖而不是加到链表

	多线程同时 put 和 get 导致 get到 null：
		本质：一个线程触发扩容，开始重新哈希计算，另一个线程同时获取，此时找到了key，value却是指向了新的，原有的没了

	线程安全包装： Collections.synchronizedMap(new HashMap<Object, Object>(16))
		或者使用Hashtable，ConcurrentHashMap

HashMap在链表节点过深的时候为什么选择红黑树
	红黑树属于二叉树，（二叉树分为：二叉查找（搜索）树，强平衡(自平衡)二叉查找树，弱平衡二叉查找树）
		二叉查找树 BinarySearchTrees BST 
			每个节点最多只能有两个子节点，左子树的键值小于根的键值，右子树的键值大于等于根的键值。
			二叉查找树的节点进行查找，高度为 n，查询次数为 n。时间复杂度依赖于节点高度。
			极端情况，键值是顺序增大的，则二叉查找树退化为链表。
		平衡二叉查找树 Balanced binary search trees  AVL Trees（两个人名 前苏联的）
			AVL树在满足二叉查找树的前提下，还需要满足 任何节点 的两个子树的高度差最大为一，所以是呈现一种左右平衡的状态
			height <= 1   属于强平衡二叉查找树
			当我们向平衡二叉树中插入或删除节点时，会打破原有的平衡，那么它会通过旋转（左旋右旋）来恢复平衡
			这种旋转会改变节点的指向，来保证平衡，效率不高，比较耗费资源。实际中使用较少。
		红黑树 red black tree
			约定：节点只有两种 红的 黑的。根节点和叶节点（即指树尾端NIL节点）都是黑的
				如果一个节点是红的，那么它的两个子节点都是黑的（不可以连续两个红节点，可以连续连个黑节点）
				任意节点到叶节点的链路中，包含的黑节点数目相同
			节点的子树的高度差可以大于1，属于弱平衡二叉查找树


HashMap为什么选择红黑树;
	红黑树是弱平衡二叉查找树，相同节点个数情况下，旋转次数比AVL树要少。AVL为例追求强平衡付出的代价较大。
	相同节点个数情况下，AVL树的高度 <= 红黑树，只查找的化稍优
	综合插入，删除，查找的性能比较，HashMap选择了红黑树


HashMap：什么是哈希碰撞
	对于不同的关键字 key，通过hash计算可能得到同一个哈希地址（数组下标）。
		hash冲突只能尽可能减少发生的概率，无法避免。
		hash冲突过于频繁，则会槽位下挂链表，再多变为红黑树
	解决方法：
		（解决了hash冲突不就更快触发扩容了吗，，，，）
		优化hash算法
		增加数组长度
		触发数组扩容后，所有数据会进行重新hash运算重新排布
		开放定址法：发生冲突，按照某种算法查找其他空的槽位（例如顺移多少位）
		再hash法：发生冲突，则再次使用hash函数进行计算，直到不冲突
		HashMap使用的：链地址法（拉链法）
			将冲突的元素以链表的形式进行存储，只要哈希地址相同，就插入到同一个链表中，可以是头插法（1.7），尾插法（1.8）
			如果链表长度继续增加。当数组长度大于64，且某个链表长度大于8，则该链表被转换为红黑树（1.8），提高查找效率。OlogN
			转换的方法  treeifyBin 。先判断长度是否大于64，否则就先扩容 resize();

	1.7之前  Segment[] 分段锁(ReentrantLock 可重入锁实现 初始化时指定大小) + HashEntry[] 可扩容  + HashEntry链表/红黑树

ThreadLocal：为什么会导致内存泄漏
	ThreadLocal的实现原理是把 ThreadLocal的this引用作为key，用户指定的值作为value，set到线程的 threadlocals 属性字段中。
	而 threadlocals字段是 ThreadLocalMap，它的底层存储的 Entry 的 key 是 弱引用 extendsWeakReference<ThreadLocal<?>>
	
	如果线程正常结束，线程引用Entry[] 正常清除，jvm的GC会进行回收，不会引发问题。
	如果线程没有回收和销毁，例如线程池中的核心线程，使用后会归还。
		此时被引用的Entry[] 不会销毁，数组中保存的键值对不会被释放。随着累计，内存占用越来越多，导致内存溢出泄露。
	核心原因是线程依旧存在（线程池），即使Entry的key是强引用了，但是原来的线程依旧引用Entry[]数组，其内存得不到释放。

	处理方法：
		当调用set get 方法时，ThreadLocal会检测key为空的所有Entry，将其释放
	处理方法：
		当该线程的任务结束后，使用try -- finally语句块，手动清除Entry[]
			threadLocal.set();      // 只要用了threadLocal的set，结束了就一定要remove() 就像IO流必须手动关闭
			threadLocal.remove();
		就可以确保不会内存泄露

Thread：线程池相关 execute() 和 submit() 的区别
	execute() 只能提交Runnable，无返回值。subbmit可以提交 Runnable无返回值 和 Callable 返回值Future
	execute() 方法是 Executor接口中定义的，submit() 方法是ExecutorService接口中定义的，而ThreadPoolExecutor是ExecutorService的实现类
	execute() 方法执行遇到异常会直接抛出，submit() 执行任务遇到异常时不会直接抛出，只有在调用Future.get() 方法获取返回值时抛出异常。

	为什么submit()方法不会直接抛出异常
		submit方法首先会将Runnable转换为返回值为空的Callable
		然后包装为FutureTask      执行execute(ftask)
		对于FutureTask，有状态码 private volatile int state 0-6 0：new

		底层的执行是addWork 然后调用 work 方法，work来调用线程任务的 task.run() 方法
		如果任务的执行run中出现了异常，会被捕获catch(Throwable ex)，同时将结果置为空，
			同时将异常对象添加 setException(ex) 到 FutureTask 的成员变量 outcome 中。并没有抛出。
		只有读取结果 future.get() 时，拿到成员变量中的异常信息，才会抛出

	对比：execute()方法会直接抛出异常
		没有包装成futureTask而是直接传Runnable。在work的时候，从 futureTask 为 firstTask。 都有task.run()
		然后并没有对其包裹try catch，就直接抛出了

JVM：继承关系：双钱委派机制/模型

		加载一个类，自己先不加载，向上交由双亲加载。
		双亲加载不了，向下委派去自己加载。
			
		自底向上检测--是否加载成功
		自顶向下尝试--加载

			类加载器

		Bootstrap ClassLoader     系统类加载器		Java核心类库

		8之前 Extension ClassLoader		扩展类加载器		引入外部的jar包、插件扩展等。
		(JDK9之后 Platform ClassLoader)		平台类加载器

		App ClassLoader				应用类加载器    Classpath		应用类，就是自己写的类。首先都交给app来加载

		Custom ClassLoader			自定义加载器 继承ClassLoader    加载其他自定义的、特殊的目录下的类

	加载String类，首先是由App ClassLoader负责加载，但是将其委派给上一级的Extension ClassLoader，然后再委派给上一级的Bootstrap ClassLoader
		找到了java.lang.String 加载成功

	如果是加载某个ext扩展类，依旧是先发给appClassLoader去加载，然后逐级向上委派，然后bootstrapClassLoader没找到
		这时bootstrapClassLoader就会 委派 下一级的 ExtensionClassLoader去尝试加载
		ext加载成功
	
	如果是自己写的 user.java。上述都一样，逐级向上委派之后，逐级向下委派
		ExtensionClassLoader没有找到，向下委派到AppClassLoader 在Classpath下加载成功。

	如果AppClassLoader也没有找到，就报错 ClassNotFoundException 异常。常见于jar包版本不兼容等情况。

	为什么都首先交给AppClassLoader加载，因为应用程序的main入口在app类加载器负责的范围中，就是自己写的类

		并且Java处于安全考虑，自己写的代码，类。是不可以使用java核心类库的包名的。避免重名和混淆。

	保证类的唯一性


JVM：如何突破双亲委派机制
	可以：类加载器中有一个自定义类加载器 Custom ClassLoader
		重写其中的loadClass方法，使其不进行双亲委派即可
	
	Java 核心 Launcher包中，存放着类加载器 AppClassLoader   ExtClassLoader
		BootstrapClassLoader 是c++的本地代码不显示在java中。
	
	主要的方法 loadClass
	从URLClassPath ucp中可以看出所有待加载的类路径包路径。
		例如jdk/jre/lib   核心类
		target目录下的自己编写的类
		以及扩展的 repoistory 例如springframwork/boot/spring-boot-starter
		如果是idea编辑的 还会有idea支持的测试工具插件等的jar包

	调用父类加载器：
		return super.loadClass(var1, var2);

	类加载器的顶级父类（抽象类）
		ClassLoader

	其他的中间的实现类 例如 URLClassLoader SecureClassLoader都没有实现loadClass方法
		所以调用 某个类加载器的parent去加载时候，都会调用顶级类的ClassLoader中的loadClass方法

	ClassLoader中的loadClass方法就是实现双亲委派的核心逻辑。
	protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException{
		synchronized(getClassLoadingLock(name)){

			首先check当前类是否已经被加载了----找到了返回
			没有找到则调用appClassLoader的parent----ExtClassLoader的loadClass去执行
			ExtClassLoader的loadClass则尝试调用ExtClassLoader的parent的loadClass
				因为是c++实现的BootstrapClassLoader   ExtClassLoader的parent是空
			parent没空则调用BootstrapClassLoader的方法findBootstrapClassOrNull----找到了返回
			Bootstrap类加载器没能加载到，调用Ext加载器的findClass方法来加载----找到了返回
			没找到则递归回到上一层 用App加载器的findClass方法加载----找到了返回
			没找到报错
			所以报错是ClassNotFound，而不是ClassNotLoaded
				
			Class<?> c = findLoadedClass(name);
			if(c == null){
				long t0 = System.nanoTime();
				try{
					if (parent != null){
						c = parent.loadClass(name, false);   
					}else{
						c = findBootstrapClassOrNull(name);
					}
				}catch(ClassNotFoundException e){
				
				}
				if(c == null){
					long t1 = System.nanoTime();
					c = findClass(name);

					sun.misc.PerfCounter.getParentDelegationTime().addTime(t1-t0);
					sun.misc.PerfCounter.getFindClassTime.addElapsedTimeFrom(t1);
					sun.misc.PerfCounter.getFindClasses().increment();
				}
			}
			if(resolve){
				resolveClass(c);
			}
			return c;
		}
	}

	具体还有不同loadClass findClass方法重载（参数列表不同）来完善判断逻辑

	核心逻辑：带有synchronized()锁块保护的递归思想，也体现了synchronized锁的可重入性。

	故此，自定义类加载器继承 ClassLoader 覆盖掉这个核心的 loadClass 方法就可以跳出双亲委派机制


JVM：什么是内存溢出
	OutOfMemory  OOM   -----jmap
	指程序在申请内存时，没有足够的内存空间供其使用，抛出OOM错误。
	指没有空闲内存，垃圾回收器GC回收后也不能提供更多的内存空间。
		突然某些实例大量增加，可能就是访问量突然增加了。

	注意 OOM溢出的是堆内存，是对象没法被清理堆积过多导致。

	栈内存是每个线程执行时自行分配，存有方法调用栈，局部变量等。如果递归次数过多，调用链过长。
		可能导致栈内存使用过多进而导致 栈内存溢出错误   StackOverflowError    ----jstack

	发生OOM后，其他线程是否可以继续工作
		要视情况决定：
			OOM是堆内存溢出
			如果发生oom，是线程栈内部发生的，报错，线程栈执行结束，销毁。那么GC可能会强制清除该线程栈所有的堆内存
				里面的数据也就全部丢掉了，造成数据丢失
				如果再有新的正常线程过来就依旧正常处理。	

			如果发生oom的是一个全局性的对象，引用被其他全局的无法被GC清理的对象持有等情况，就无法销毁，内存无法释放
			并且也需要考虑对象的生命周期（Spring框架下）以及变量的范围，全局变量，局部变量。
				如果一个spring的单例bean持有一个会oom的全局变量的引用，那么它oom之后也GC无法释放内存。
				就会导致一直堆内存爆满，导致无法进行任何操作了，再过来正常请求也无法处理。

		主要判断依据就是：发生OOM后，对象能否销毁，GC能否清除内存

		jvm内存可视化监控工具
			visualvm     bin目录下启动
			可以可视化的看到堆内存，GC的情况

JVM：什么是内存泄露
	Memory Leak
	指程序运行后，没有释放所占用的内存空间（有引用在引用对象，无法释放，GC无法回收）
	一次内存泄露可能影响不大，但长时间多次数的内存泄露发生堆积，占用大量内存，就会产生内存溢出

	常见情况：单例对象，生命周期与应用程序一样长（不会主动回收的对象）。如果该单例对象持有对外部对象的引用。
		那么这个外部对象在使用结束后是无法被回收的，就会产生内存泄漏
	
	常见情况：资源的关闭。例如数据库连接JDBC，网络链接socket，IO流stream，ThreadLocal等
		都必须在finally语句块中close，或try with source来在使用后关闭。
		否则都不会被GC回收


JVM：如何配置线上环境
	JVM：栈、堆、元空间

	默认的：栈 1m，设置 -xss512k，
		也就是默认一个线程是1m。如果项目中可能有300个线程，那么默认线程就用了300m

	堆(关键)：大概将机器的一半内存分配给堆，新生代，老年代
		CMS: 1/3   2/3    CMS垃圾收集器的新生代和老年代所占的比例  适合堆比较小 8g以下的情况
		G1: 6:4  G1垃圾收集器的新生代:老年代比例     适合堆比较大 8g以上的情况

	元空间：一般512M就足够了
		一般是用来加载类，比如项目中的各种开源框架和插件的依赖的加载
		不设置就使用物理内存。

	此时JVM的配置参数是：以4核8g为例
	-Xms4096M -Xmx4096M -Xss1M -XX:MetaspaceSize-512M -XX:MaxMetaspaceSize=512M -XX:+UseG1GC

	可以添加参数 -XX:+HeapDumpOnOutOfMemoryError

JVM：高并发环境的优化策略（重要）
	思路与经验的考察

	例如：2020年天猫双11，全球狂欢季，订单创建峰值 58.3万笔/秒
		2023年天猫双11，全周期累计访问用户数超8亿

	内存预估：
		以一台4核8g内存服务器为例，单机最大并发请求在300-400之间。
		如果请求需要2000台机器同时处理，一个订单容量1KB。
		一台机器就是 300*1KB*20（其他相关操作）*10（其他相关对象） 的内存开销，
			这些是在jvm的新生代中创建，朝生夕死，一秒后使用完成，成功响应，60MB的对象进入垃圾回收 90%都会销毁。
		（实际远远要更加复杂，可能有众多性能不同的服务器，服务器之间需要进行调度，服务器上还同时运行有很多其他的微服务程序）
		（订单包含的信息以及用户数据也不会相同，可能有的很大有的很小。也有很多与订单生成的相关业务需要同时执行。生成订单也需要调用其他的微服务）

	高并发对于jvm的影响：
		堆：大量的请求对象，大量的与数据库交互的对象以及接收结果数据的封装对象，大量需要返回前端的dto对象和json。
		栈：大量线程并发执行，

	内存分配：
		4核8g的机器，分给一半给jvm，其他留给操作系统以及其他中间件。
		堆 3g，新生代1.5g，老年代1.5g。（需要调整的地方之一：新生代与老年代的比例） ------ new User()
		栈估算：一个栈1mb，处理300个请求预估总线程500，那么就是占用500MB
		元空间（永久代）（方法区）默认512MB---------User.class

	JVM配置参数：
		-Xms3072M -Xmx3072M -Xmn1526M -Xss1M
		-XX:MetaspaceSize=512M -XX:MaxMetaspaceSize=512M
		-XX:+PrintGCDetails
		-XX:+PrintGCDateStamps
		-Xloggc:d:/gc.log
		-XX:+HeapDumpOnOutOfMemoryError
		-XX:HeapDumpPath=d:/heap.hprof
		打印gc日志，oom时的heap快照

	内存占用动态推算
		新生代分为 Eden区 80%，S0区（FromSurvivor）10%，S1区(To Survivor)10%
		1.5g的新生代，60m每秒生成，那么25秒新生代Eden占满，触发MinorGC （ParNew 是很快的，一般都是毫秒级）
		一般情况下，一次可以回收掉90%的新生代（Eden + S0）对象，那么新生代还存活150MB，也就是S0 S1大致需要的空间。
		-XX:SurvivorRatio  默认是8 就是 8：1：1  那么就是1.2g：150M：150M
		有可能就有的放不下进入了老年代。如果老年代持续堆积，就会触发FullGC，是十分消耗性能的，jvm会暂停
		所以新生代需要以Eden区为基准进行计算

	优化分配老年代与新生代的比例：
		新生代较小，发生一次MinorGC后，Survivor不足或者触发动态年龄判断，对象进入老年代。（Survivor空间不足）
		将新生代调整为2g，老年代1g，此时Eden：1.6g，S0 200m，S1 200m （依旧保持默认的 8：1：1）
		参数
		-Xms3072M -Xmx3072M -Xmn2048M -Xss1M

	对于 @Service @Controller 这类的单例Bean，SpringIoC容器没有关闭，他们是一直存活的，不会被回收的
		可能不多就几十兆，他们应该尽快被放入老年代
		修改 -XX:MaxTenuringThreshold=5  默认是 15.就是对象在S0区和S1区之间不断复制整理，切一次年龄增长一岁，到达15岁进入老年代。
		改为5岁就加入老年代。也就是新生代5次垃圾回收都不能回收该对象，那么就放入老年代。（默认是15次）

	对于项目中的大对象，例如数据库字典数据，配置数据，初始化数据。
		这些内容需要直接进入老年代，
		修改 
		-XX:PretenureSizeThreshold=1M  阈值，对象大于1M，直接放入老年代

	选择合适的GC垃圾回收器
		修改 
		-XX:+UseParNewGC  多线程的新生代的垃圾回收器  -XX:+UseConcMarkSweepGC   CMS垃圾回收器适合于内存比较小的服务器
		G1垃圾收集器适合于内存比较大的情况

	高峰期时间与容量的计算
		按照每隔几分钟MinorGC，200mb被放到S1，五岁进入老年代
		估算大只要一小时，才会有1gb进入老年代触发FullGC。
		如果不是高峰期，可能要几个小时才会触发老年代的FullGC（在高峰来之前手动GC清理老年代）
		增加配置，老年代达到75%就触发FullGC。触发FullGC后，需要内存整理，触发此处为0就是每次都整理。

	最终JVM配置：

		-Xms3072M -Xmx3072M -Xmn1526M -Xss1M
		-XX:+UseCompressedClassPointers
		-XX:MetaspaceSize=512M -XX:MaxMetaspaceSize=512M
		-XX:+PrintGCDetails
		-XX:+PrintGCDateStamps
		-Xloggc:d:/gc.log
		-XX:+HeapDumpOnOutOfMemoryError
		-XX:HeapDumpPath=d:/heap.hprof

		-XX:+UseCMSCompactAtFullCollection
		-XX:CMSFullGCsBeforeCompaction=0

优化思路总结：
	尽可能让对象在新生代里面分配和回收，避免对象频繁进入老年代频繁FullGC
		也就是要分清楚，哪些对象是要快用快收的。
	给系统充足的内存空间，避免新生代频繁的垃圾回收，调整新生代与老年代的比例
	指定合适的垃圾收集器

	准备提交事务，执行器将 binlog 写入磁盘   ------ 主从复制  记录了数据的变化

	写入binlog文件与位置   ----- 传到IO供从库监听
	写入commit标记。事务提交完成。   -------  commit

	InnoDB存储引擎的IO线程将 缓冲池 中修改好的数据写入磁盘   ----- 真正更改磁盘上的文件

MySQL：详细了解B+Tree，为什么不用其他的数据结构
	
	关键：高度与查找效率；按页存储磁盘预读效率高；

	二叉查找树  BST  Binary Search Tree
	平衡二叉查找树 AVL Tree    Balanced binary search tree
	红黑树 Red-Black Tree
	多路平衡查找树 Blanced Tree （B Tree）
	改进型多路平衡查找树 Balanced+ Tree  （B+ Tree）

	二叉查找树：查找时间复杂度依赖于节点深度，查找效率低。两个子节点数据量大树就很高。
		如果数据顺序增大则退化为链表
		并且BST是高度不平衡的，查找删除与插入效率与树的高度相关。
		并且查找数据，每一个节点都要进行一次IO读取，高度越高，效率越低
		并且每个节点只能存储一个数据，磁盘块的利用率很低，性能无法发挥，无法发挥磁盘预读功能。

	局部性原理：计科，描述了程序在访问存储器时的局部性行为。
		根据局部性原理，CPU在访问存储器时，无论是存取指令还是读取数据，
			所访问的存储单元都区域聚集于在一个较小的连续区域中（也就是读一片）
		时间局部性：
			如果一个信息正在被访问，那么近期他很可能还会被再次访问
		空间局部性：
			在最近的将来要用到的信息，很可能与现在正在使用的信息在空间地址上是临近的。
		顺序局部性：
			在程序中，大部分指令都是顺序执行的，顺序执行和非顺序执行比例约为5：1

	磁盘预读：
		机械磁盘：涉及到磁盘的转动，对于找数据，是非常耗时的
			寻道时间+旋转时间
		为了尽量减少IO操作，计算机系统一般采用预读的方式，预读的长度一般为页 page的整倍数。
		
		页是计算机管理储存器的逻辑块。硬件及操作系统中往往将磁盘存储区分割为连续大小相等的快。
			每个存储块称为一页，在许多操作系统中，页的大小通常为4k
		当程序要读取的数据，首先是读取主存，如果主存中不存在该数据，就会触发缺页异常。
			此时系统会向磁盘发出读盘信号，磁盘会找到数据的起始位置并向后连续读取一页或者几页。
			加入内存，然后返回，程序继续运行。
		根据局部性原理，程序运行期间所需要的数据通常比较集中。
			当一个数据被用到时，其附近的数据也会通常马上会被使用。
			所以读取磁盘采用磁盘预读的方式，因为磁盘顺序读取的效率很高。
			所以即使只需要读取一个字节，也会读取一页甚至多页的数据

	平衡二叉查找树AVL Tree
		任意节点的子树的高度差最大为一。提高了二叉查找树的查找效率。
		维护平衡的代价很高，每次增加或者删除节点都会多次旋转去维护平衡状态。
		其他的缺点同BST（树太高，节点存的少）

	红黑树
		任意节点到叶节点的链路中都包含相同数目的黑节点
		相比于AVL，旋转次数变少了，但于大局没有影响。
		其他缺点同上

	多路平衡查找树 Balance Tree
		每个B Tree的父节点有多个子节点，平衡是意味着左右分布均匀。
		每个节点最大可以存放 路数-1个分支
		每个节点最大可以有 路数 个分支
		在非底层的节点中也存储了数据
			
	B Tree的数据存储（指针：子结点指针   键值：索引键   数据：表记录中除了主键之外的数据）
		指针  键值  指针  键值  指针 .....
			  数据        数据

		指针  键值  指针  键值  指针 .....					指针  键值  指针  键值  指针 .....
			  数据        数据									  数据        数据

		键值  数据...		键值  数据...		键值  数据...		键值  数据...
		键值  数据...		键值  数据...		键值  数据...		键值  数据...

		缺点，每个数据都需要从顶层根节点出发去查找，相比于AVL仅仅优化了部分IO性能
		索引在数字上可能是连续的 1 2 3 4 5 6，但是对应他们每个查找的路径却不同。
			导致了性能的不稳定。
		并且相比于B+Tree，节点（页）既存储指针，又存贮键值，降低了节点存储指针的效率，
			随着层数增加，效率损失按照2的次方计算。也就是每个节点持有的子节点是B+Tree的一半。

	B+Tree的优势，改进的多路平衡查找树
		节点只存储指针（索引键），数据全部存储在叶子节点。并且所有的叶子节点以双向链表的形式链接。
		页4kb，指针和索引键都是64位的 8b 那么一个节点可以存(4096-8)/(8+8) = 255
			就是255个索引键和256个子节点指针（和一个自身地址） 2^8
			2^24 是16777216 就是所谓的2000w单表，此时索引大小 (1+256 +256*256) *4KB=263172KB=257MB（一个）
		查找时，根据索引值，按页去磁盘读取索引到内存中。

		叶子节点是一个顺序增长的双向链表，很方便的定位前后数据，范围查找优势很大。
			查找树找到范围查找的起点，然后利用链表读取范围，还可以利用磁盘预读的优势。

	B+ Tree的数据存储
		指针  键值  指针  键值  指针 .....

		指针  键值  指针  键值  指针 .....					指针  键值  指针  键值  指针 .....

		双向链表（数据）

	总结：
		B+Tree 中间非叶子节点没有数据只有索引，相同的磁盘页节点越多，数据量一样B+树高度更低，IO更少
		B+Tree每次查找必须查找到叶子节点，性能稳定
		B+Tree的范围查询更有优势


MySQL的索引：
	为什么建议用自增数字作为主键索引：
		自增主键时连续的，插入过程中能减少页的分裂，当一页写满就会在当前索引节点页的后续位置开辟一个新页，减少数据移动。
		非自增主键往往不连续，例如UUID是随机的。新纪录就会被插入到现有索引页中间的某个随机位置。
			导致原来索引页的数据发生移动。频繁的移动会带来很多开销。带来很大索引维护的消耗。
		可以自己定义全局唯一ID的生成逻辑，既满足顺序自增，又有随机性与唯一性。
			例如拼接 自增 + 时间戳 + 设备ip网络ip + 雪花算法给了4位毫秒级的重复量 +请求code消息code之类

	主键：
		InnoDB会选择主键作为主键索引，
		没有主键，InnoDB会选择第一个不包含有Null值的唯一索引作为主键索引。
		如果上述都没有，InnoDB会选择内置的6字节长的ROWID作为主键索引，是随着行记录的写入而递增的。


MySQL：索引的一些叫法
	主键索引：

	辅助索引，也叫二级索引  Secondary Index 使用主键之外的字段建立索引。
		二级索引中的叶子节点只存储了索引字段的值和主键值，不包含完整的表记录。
		你要是说这表就两个字段当我没说，

	聚集索引也叫聚簇索引 Clustered Index，非聚集索引，也叫非聚簇索引。
		主键和数据在一起的索引叫聚集索引，聚簇索引的叶子节点存储了整个表的行数据，
			主键索引就是一种聚集索引。
		主键和数据不在一起的索引叫非聚集索引，
			上述的二级索引，或者MyISAM的索引（没存数据，存的是数据的地址）是非聚集索引

	回表查询：
		当通过二级索引查询数据时，InnoDB 会首先在二级索引的 B+Tree 中查找匹配的索引键值，
		然后通过存储在叶子节点中的主键值回表到聚簇索引（主键索引）中获取完整的行数据。

	索引覆盖：可以用来优化SQL语句的执行效率
		查找的字段是添加了索引的字段。用索引的体积（空间）换执行效率（时间）
		之查找一个字段，该字段在索引上只需要走索引，不需要回表查询。就大大提高了效率。

	联合索引：
		对于想要同时查找多个字段，就在多个字段上建立联合索引，
			联合索引将同时包含这多个字段的数据和主键数据。
			这样在根据其中某一个字段查找时，就可以直接根据索引找到所有查询所需字段的数据，无需回表。
		用更大的空间来换执行效率。

	索引下推：Index Condition PushDown 简称ICP
		MySQL 5.6新增特性，主要作用是用来减少回表查询的次数，提高查询效率。
		连接层 ---- Server层 ---- 索引引擎层 ---- 数据层
		多个查询条件，xxx and xxx 
			如果有查询条件的字段上有索引，多个字段有联合索引。
			那么查询条件都会在索引中判断。
		如果多个查询条件例如三个条件，只有两个有联合索引，
			那么在联合索引筛选完毕，回表到主键索引拿到全部行数据后，
			交给Server层对于第三个条件再进行过滤
		也就是只要有索引就优先走索引去筛选，减少回表要查询的数据

			默认SpringBoot使用的式SimpleAsyncTaskExecutor，结合之前的线程池知识，我们可以自定义线程池来最大化性能
				@Bean(name = "taskExecurtor")

					new ThreadPoolTaskExecutor  (是Spring对于ThreadPoolExecutor的一个封装)
					配置好线程池参数
				}

			其实就是java线程池的Spring形态（ @Autowire注入），原来线程池中任务的编写，调度以及定时，spring都可以相应实现
		
		异步任务的编写与提交

SpringBoot默认是JDK动态代理还是CGLIB动态代理
	CGLIB动态代理：
		spring.aop.proxy-target-class = true 默认true就是CGLIB动态代理，false就是JDK动态代理
	原因：
		JDK动态代理是基于接口的，也就是代理类和被代理的类要实现一个公共接口，
		注入的时候例如写实现类 @Resource private GoodsServiceImpl goodsService 就会报错。
			有可能导致意外的类型转换异常
		
		而CGLIB动态代理是基于继承的，可以代理任何类型的目标类。
			除了被final修饰的类，final修饰的方法，不可被继承也就无法代理。

		所以CGLIB可以涵盖所有JDK动态代理的情况，SpringBoot为了保证AOP功能可以应用与任何类型的Bean，无论是否实现接口
			采用CGLIB作为代理的实现方式

SpringCloud：的理解，在整个微服务体系中的作用
	为开发人员提供了一套集成好的微服务解决方案，不在需要自行集成各类组件去解决不同问题。降低了开发难度
	SpringCloud提供了统一的标准。为Spring生态注入了更强大的生命力。
		常见问题：负载均衡，服务注册，配置管理，服务调用，路由拦截，熔断限流等等


SpringCloud：服务熔断，服务降级
	服务熔断：当服务A调用服务B时，如果此时服务B不可用，那么上游的服务A为例保证自己不受影响，旧切断调用服务B，防止服务雪崩发生，
	提前做好一种兜底措施，例如返回预先准备好的数据，或者记录数据信息到数据库，redis中，后续进行补救。

	服务降级，上述的B服务用不了了，就采用备选方案C服务，C是消耗很小的也不会提供很多服务，降低B受损的影响。
		当系统高负载过高时，对非核心的业务服务进行关闭，来保证核心业务的正常执行。

	比较：都是为了保证服务的可用性，防止系统整体负载过大。
			都是表现出部分服务暂时不可用的状态
	不同：服务熔断通常是下游服务故障引起。
			而服务降级是从系统整体符合考虑

SpringCloud：为什么要对项目系统进行拆分。
	单体 --->  微服务 分布式

	单体项目的劣势：
		(团队协作)
		项目随着业务功能的增加，功能模块增多，业务复杂度增大，代码量也增加，在多人团队中，
			各开发人员为了实现自己的功能，有时候经常需要修改另一个开发人员的代码，经常会出现代码的冲突;

		(耦合度高)
		一个地方的功能修改经常导致另外一个地方的功能出现异常;

		(只能整体测试)
		每次一个小小的修改，都需要测试团队对很多功能进行测试，效率非常低，测试团队也充满抱怨;

		(扩展性，健壮性差)
		每次新增新的需求，开发效率都比较低下，由于所有功能都在一个项目中，导致业务代码逻辑变得非常复杂，
			经常陷入牵一发动全身的状态，团队成员也不敢轻易修改代码，响应新需求的速度低:

		(维护难度高)
		由于所有功能在一个项目中，代码量极大，代码的可读性可维护性可扩展性都变得很差，也导致团队成员不稳;

		(结合上述健壮性差，测试难度高----升级迭代难度高)
		出现一些更好的新技术，也不敢轻易升级技术，升级非常困难，升级可能产生各种问题，调试和测试会消耗大量的时间和精力，团队生成力极低;

		(只能整体上下线)
		项目迭代上线效率低，每次上线，全体成员，技术团队、测试团队、运维团队都需要加班加点，而且常常都是胆战心惊的;

	微服务分布式的优点：
		代码拆分：即使总代码几十万行，但是每一个服务的代码也就几万行，由几人的小团队来维护
			团队只需要专注于自己的业务，其他的调用接口，api，RPC即可

		上述拆分，也会带来代码冲突降低的好处，且每个服务可以单独测试，测试难度降低。

		新增业务需求只需要新增服务即可，然后去调用原有系统的微服务接口

		每个模块功能细分，可以追求当前领域的新技术，高效迭代进化。

		上线更新与维护，以服务模块为单位，哪个好了上那个，需要升级就下下来。


SpringCloud的注册中心
	Nacos，Eureka，Zookeeper（Dubbo），Apollo（携程的），Consul

	相似点：提供服务注册和发现功能。支持服务的心跳机制健康检查。支持高可用。

	不同点：
		Nacos支持主动对微服务进行状态检测，临时实例采用被动心跳检测，永久实例采用主动检测。
			临时实例心跳检测如果不健康则会从注册中心中阐述，永久实例（本地内嵌数据库或者链接mysql）不会删除
			支持服务列表变更时的主动消息推送，服务列表更新会更加及时。
		Nacos集群支持两种模式，默认是AP模式，当集群中存在非临时实例时，采用CP模式
			而Eureka只支持AP模式
		Nacos有注册中心和配置中心
			而Eureka只有注册中心
		Nacos具备优秀的后台管理界面，用于服务上下线以及流量管理负载均衡以及配置的编写
			而Eureka的后台只能查看，需要使用api手动调用完成服务的上下线且不具备负载均衡
		Nacos由SpringCloudAlibaba开源维护
			而Eureka已经闭源了

	注册中心应该是AP还是CP
		AP，优先保证一致性。微服务框架一般都提供了服务容错和重试功能。减轻注册中心的压力
		如果采用CP，那么每当有服务实例上线下线，都需要等待注册中心集群中的数据完全一致才算注册或删除成功。
			如果应用实例频繁上下线，会导致注册中心压力增大，服务注册与发现的效率降低。


SpringCloud：ACID、BASE、CAP理论
	ACID是传统数据库中常用的理念，追求的是数据的强一致性。
		Atomicity 原子性
		Consistency 一致性
		Isolation 隔离性
		Durability 持久性

	BASE理论是在分布式环境下，牺牲强一致性来换取高可用性的策略。
		Basically Available 基本可用，
			部分系统故障时，允许损失部分可用性
		Soft State 软状态：
			允许系统在不同节点的数据副本之间进行数据同步的过程允许延时。允许中间状态（主从复制的延迟）
		Eventually Consistent 最终一致性：
			所有的数据副本，在一段时间的同步之后，最终能够达到一致，而不是实时一致

	CAP理论是指 分布式系统中，一致性，可用性，分区容错性不可能三角，要么CP，要么AP
		Consistency 一致性
		Availability 可用性
		Tolerance of network Partition 分区容错性
			网络故障时，系统仍能继续工作

		CP：一致性优先，牺牲可用性来确保一致性

		AP：可用性有限，允许短暂的不一致存在，但是通过最终一致性确保一致。


SpringCloud：接口的幂等性
	唯一请求ID + redis （Controller接口幂等）

	概念：Idempotent 抽象代数中：N次变换与1次变换的结果相同
		幂等函数或者幂等方法，是指可以使用相同的参数重复执行，并能获得相同结果的函数。
		对于编程而言，某个方法使用相同参数调用多次与调用一次，对于其业务指责而言产生的效果是相同的。
			并且不会导致系统数据出错，那么它就具有幂等性

		也就是用户对于统一操作发起的一次请求或多次请求锁产生的影响是一样的，不会因为多次调用（点击）而产生副作用

		幂等性也就是 多次执行无副作用（副作用就是对结果产生变化，破坏或者不可预料的结果）

	场景：
		网络波动导致的重复请求

		用户重复操作，重复下单，重复触发躲避交易

		应用的失败或者超时重试机制（RPC重试，业务层重试逻辑等）

		定时任务的重复执行

		第三方平台的接口回调，例如支付成功回调接口，因为异常导致多次回调

		中间件根据自身的特性，也有可能进行重试

		用户重复点击提交按钮或者重复刷新页面

		使用浏览器误操作，重复提交表单，例如后退操作，历史记录等

		浏览器重复的HTTP请求

	如何设计接口的幂等性：
		对于分布式微服务的架构，首先要名且在哪一层解决幂等性

		展示层 --- 接入层（网关，认证中心） --- 业务层 -- 数据访问层 --- 数据层
					   日   志   系   统   与   监   控   系   统

		前端可以进行防抖操作，以及适当的拦截。

		对于数据的查询操作，利用布隆过滤，缓存响应结果，redis缓存，优化数据库等方式提高效率。幂等性要求不高，

		业务层针对每个特定的微服务所面临的请求类型与数量，制定相应的幂等性策略。
			例如 用户中心，商品中心，订单中心，消息中心，通知系统，积分系统等等
		重点关注的是对于数据的 修改 操作，也就是数据访问层的调用要保持幂等。
			
	解决方案：
		插入mysql的操作，可以使用唯一性限制，唯一索引，插入重复的数据会报错。

		Token（全局唯一请求ID） + redis缓存
			前端携带token或者唯一请求ID，或者后端生成绑定此次请求对象。将请求ID进行缓存。
			之后处理请求，根据业务需求缓存该次请求的响应结果json，
				如果处理成功，就打标记该ID已处理完成，redis设置过期时间
				短时间内的相同请求ID过来，不予处理，或者返回上次请求的结果
				
			确保前端发送相同请求会携带相同的请求ID，如果期间没有其他修改操作，可以直接返回缓存中的结果
				如果就清空上次缓存


SpringCloud：分布式事务 ---- 看多少个数据源连接池
	redis redission 实现分布式锁

	redis的lua脚本保证多个redis操作原子性

	方案：2PC、3PC、TCC、本地消息异步确认、可靠消息最终一致性、
	
	解决框架：Seata（实现了增强版2PC，TCC）、RabbitMQ（半消息+超时检查）

	事务是保证对数据库进行多个读写操作的一致性。
		推荐尽量避免，会带来系统的复杂性与效率低下。

	分布式事务是要保证多个计算节点（多个链接）对于多个数据节点（多个库）的操作的原子性，要明确所保护的粒度。

	本地事务，仅支持单库事务。

	Spring的事务管理只能管理单个数据源链接池的情况

	重点就是同时有几个数据源链接池


SpringCloud：分布式系统的限流
	Gateway 路由断言工厂  限流熔断降级

	redis计数器实现限流、令牌桶限流算法

	计数器：每次请求计数+1，计数器值大于60并且与第一次请求在1s内，就拒绝，达成1s 60次的请求限流。但是要每秒重置计数器。

	令牌桶算法：redis维护一个桶，桶内令牌的增加速度一定，请求过来持有令牌才可以进行下一步去处理（令牌可以是全局唯一ID绑定请求）
		没有拿到令牌的在外面一个队列等待。队列满了抛弃请求返回繁忙。--429 TooManyRequests

	Nginx限流：
		配置 ngx_http_limit_req_module 模块
		nginx.conf
			limit_req_zone $binary_remote_addr zone = prip:10m rate=1r/s;
			limit_req_zone $server_name zone = perserver:10m rate=2r/s;
	
	OpenResty限流（Nginx扩展版 可以使用Lua脚本实现限流逻辑编写）

	Sentinel限流 管理后台配置

	Redis+Lua脚本限流 配合AOP实现，拦截请求，

	SpringCloudGateway限流  RateLimiter Filter ---- Bucket4j
